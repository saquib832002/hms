# Upgrading a live deployment

A one-off runbook for the first upgrade after the initial deployment. The
routine procedure is [`DEPLOY.md`](DEPLOY.md) §11 and it is four commands; this
is longer because this particular upgrade is not routine, and the reasons are
worth reading before you start rather than discovering at step 6.

---

## 0. What makes this one different

**Twenty-eight migrations are pending.** The initial deployment ran
`20260823201142_init` and possibly a few after it. Everything from the pharmacy
billing work onward has only ever been applied to a development database.

**Thirteen of those create tables carrying `tenantId`.** A new table has **no
RLS policy until `npm run db:rls` applies one**, and a table with no policy is
readable by every hospital. On a single-tenant deployment that is invisible; the
day a second hospital exists it is a breach. `db:rls` is not optional here and
it is not in the §11 command list.

**Every migration in this repo is hand-written.** The Prisma schema engine
cannot be downloaded on the machine they were authored on, so none of them was
generated by `prisma migrate dev` and none has been checked by
`prisma migrate diff` against a database holding data. They are careful and they
are reviewed, and that is not the same as tested.

**Therefore: rehearse on a restored copy first.** §2 is the step that matters.
Skipping it means the first time these migrations meet real rows is on the
database your customers are using, and `migrate deploy` is not transactional
across migrations — a failure halfway leaves some applied and some not.

**New environment variables are required.** The API will boot without them and
silently lose features: no password-reset email, and reset links hidden on every
sign-in screen. §3.

---

## 1. Back up, and prove the backup restores

```bash
sudo -u postgres pg_dump hms_db | gzip > ~/pre-upgrade-$(date +%F).sql.gz
ls -lh ~/pre-upgrade-*.sql.gz        # a few hundred bytes means it failed
```

Then prove it, because a backup you have never restored is a hypothesis:

```bash
sudo -u postgres createdb hms_db_rehearsal
gunzip -c ~/pre-upgrade-$(date +%F).sql.gz | sudo -u postgres psql hms_db_rehearsal
sudo -u postgres psql hms_db_rehearsal -c 'select count(*) from patients;'
```

If that count matches production, you have both a backup and the database §2
needs. **Get a copy off the box** — a backup on the VPS dies with the VPS.

---

## 2. Rehearse the migration on the copy

This is the step that makes the rest safe. Everything here runs against
`hms_db_rehearsal` and cannot touch production.

```bash
sudo -u hms -i
cd /opt/hms/app && git pull
cd backend && npm ci && npx prisma generate
```

Point the CLI at the copy for one command only — do **not** edit `.env`:

```bash
DATABASE_URL_ADMIN="postgresql://hms_owner:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
  node prisma/admin-cli.js migrate deploy
```

Read the output. It lists each migration as it applies. What to watch for:

- **`20260904220000_diagnostics`** is the only one using
  `ALTER TYPE … ADD VALUE`. Postgres 12+ permits that inside a transaction; if
  this deployment is on anything older it will fail here, and this is where you
  want to find that out.
- **Any failure at all.** Note which migration, stop, and fix it before going
  near production. A half-applied set is the worst state available, and it is
  the state production would be left in.

Then the two things `migrate deploy` does not do:

```bash
DATABASE_URL_ADMIN="postgresql://hms_owner:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
DATABASE_URL="postgresql://hms_app:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
  npm run db:rls

DATABASE_URL_ADMIN="postgresql://hms_owner:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
  npm run db:constraints
```

`db:rls` prints what it applied and **self-checks both directions** — that one
hospital cannot read another's rows, and that login still works. That second
check exists because applying RLS once took sign-in down completely: two
`SECURITY DEFINER` functions stopped seeing past the policy and nobody could
authenticate. If it reports a failure, do not proceed.

Finally, boot the API against the copy and look at one screen:

```bash
DATABASE_URL="postgresql://hms_app:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
DATABASE_URL_ADMIN="postgresql://hms_owner:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
PORT=3100 npm run build && \
DATABASE_URL="postgresql://hms_app:PASSWORD@127.0.0.1:5432/hms_db_rehearsal" \
PORT=3100 node dist/main
```

`curl localhost:3100/api/v1/health` should return `status: ok`. Sign in as a real
user from the restored data and open a patient, a prescription and an invoice.
Then stop it and drop the copy:

```bash
sudo -u postgres dropdb hms_db_rehearsal
```

**Why this much ceremony:** every previous first live run in this project found
a bug that no amount of reading could — failure auditing that was unreachable
code, a login throttle that locked out the hospital rather than the attacker, a
provisioning transaction that RLS rolled back. Assume this one has one too, and
find it on a copy.

## 3. The new environment variables

Add to `/opt/hms/app/backend/.env`. The API boots without them; what it loses is
password-reset email and the links that offer it.

```bash
# The public origin of the web app. Used to build reset links.
#
# Configured, never read from the request's Host header: a link built from a
# header is one an attacker aims at their own server by sending
# `Host: evil.example`, and the victim clicking it hands over a live token.
WEB_URL="https://hms.example.com"

# smtp delivers; log writes to the API log and delivers nothing; unset sends
# nothing and hides the reset links.
#
# ⚠ In production, `log` is treated as unavailable — the links stay hidden,
#   because telling somebody to read a server log they cannot see is worse than
#   not offering the link at all. So production is smtp or nothing.
MAIL_TRANSPORT="smtp"
MAIL_FROM="OneCare HMS <no-reply@example.com>"
SMTP_HOST="smtp.example.com"
SMTP_PORT=587
SMTP_SECURE="false"          # true ONLY on 465. On 587 this must be false.
SMTP_USER="no-reply@example.com"
SMTP_PASS="…"

PASSWORD_RESET_TTL_MINUTES=30
PLATFORM_RESET_TTL_MINUTES=15
PLATFORM_RESET_GRANT_COOLDOWN_MINUTES=60
```

Two things to check while you are in this file:

**`NODE_ENV=production` refuses to start on development secrets.** `validateEnv`
rejects a `JWT_ACCESS_SECRET` containing `dev-only` or shorter than 32
characters. That is deliberate. Generate real ones, twice, and they must differ:

```bash
openssl rand -hex 32
```

Changing them signs everybody out, which is a cost on an upgrade rather than a
fresh install — do it if the current ones were ever development values, and
accept the sign-out.

**`CORS_ORIGINS` must list the public origin**, or every browser call fails with
no message worth reading.

Verify mail before trusting it, and before restarting anything:

```bash
cd /opt/hms/app/backend && npm run mail:test -- you@example.com
```

It authenticates, sends, prints the server's queue id, and reports what the
sending domain publishes for SPF, DKIM and DMARC. **Accepted is not delivered** —
a reset email that is silently filtered is indistinguishable from a broken flow,
for the user *and* in the log.

## 4. The upgrade

Take the site down for this. It is a few minutes and it avoids a request
arriving between the schema changing and the API restarting.

```bash
sudo systemctl stop hms-api hms-web

# A second dump, immediately before the change. The one from §1 is hours old by
# now and those hours are real appointments.
sudo -u postgres pg_dump hms_db | gzip > ~/pre-upgrade-final.sql.gz

sudo -u hms -i
cd /opt/hms/app && git pull

cd backend
npm ci
npx prisma generate            # BEFORE build. The client is generated from the
                               # schema, and a stale one queries columns that
                               # do not exist yet.
npm run build
npm run db:migrate             # = prisma migrate deploy, as the owner role
npm run db:rls                 # REQUIRED — 13 new tenant-scoped tables
npm run db:constraints         # partial unique indexes Prisma cannot express

cd ../web
npm ci
rm -rf .next                   # Tailwind bakes its palette at build time, and
                               # this release changes it. A stale build shows
                               # the wordmark in black.
npm run build

exit
sudo systemctl start hms-api hms-web
```

**Order is not negotiable.** `prisma generate` before `build`; `migrate deploy`
before `db:rls`; both before the API starts. `PrismaService` compares the
migrations on disk against `_prisma_migrations` at boot and warns about pending
ones — a warning, never a refusal, so a half-done upgrade starts and looks
healthy while one feature returns 500s naming a column.

## 5. Verify, in this order

```bash
sudo journalctl -u hms-api -n 60 --no-pager
```

Four lines to find:

| Expect | Means |
|---|---|
| `API listening on …` | it booted |
| `Mail: SMTP verified — the server accepted this API's credentials.` | mail works |
| no `pending migration` warning | the schema is current |
| no `DEVELOPMENT MODE` warning | `NODE_ENV=production` is set |

Then:

```bash
curl -s https://hms.example.com/api/v1/health
# {"status":"ok","database":"up","passwordResetAvailable":true,
#  "passwordResetDelivery":"smtp"}

curl -s https://hms.example.com/api/v1/platform/auth/capabilities
# {"passwordResetDelivery":"smtp","passwordResetAvailable":true}
```

`passwordResetAvailable: false` means the sign-in screens will hide the reset
link — check `MAIL_TRANSPORT`.

In a browser, and these are the ones that catch a bad upgrade:

1. **Sign in as a real user.** The sidebar must show **that hospital's name**,
   never a product name.
2. **Open a patient, a prescription, an invoice.** These exercise the
   role-shaped responses and the tenant policies together.
3. **The wordmark reads `OneCare HMS`** with `HMS` in red. All black means the
   web build is stale — `rm -rf .next` and rebuild.
4. **Request a password reset** and confirm the email arrives. Then actually
   follow the link, because `WEB_URL` pointing at the wrong origin produces a
   link that looks right and 404s.
5. **A laboratory screen and a ward board**, if those modules are sold. They
   are the newest code in this release and the least exercised.

## 6. If it goes wrong

Migrations are forward-only; there are no down migrations, deliberately — an
automated reversal of a hand-written migration is a second hand-written
migration nobody has tested. The rollback is the dump.

```bash
sudo systemctl stop hms-api hms-web
sudo -u postgres dropdb hms_db
sudo -u postgres createdb hms_db --owner=hms_owner
gunzip -c ~/pre-upgrade-final.sql.gz | sudo -u postgres psql hms_db

cd /opt/hms/app && git checkout <previous-tag-or-commit>
cd backend && npm ci && npx prisma generate && npm run build
cd ../web && npm ci && rm -rf .next && npm run build
sudo systemctl start hms-api hms-web
```

Everything written between the dump and the rollback is gone. That is why §4
takes a dump immediately before the change rather than relying on §1's.

## 7. What this does not deploy, and what is still open

**The mobile app is separate.** It ships as an AAB through the Play Console —
[`DEPLOY-ANDROID.md`](DEPLOY-ANDROID.md). Nothing here affects an installed
phone app, and an old app against the new API is fine: no endpoint was removed
in this release.

**The Android package id is unchanged** (`com.sawera.myhospital*`) despite the
rename to OneCare. Changing an `applicationId` does not rename an app, it
publishes a second one, and every existing install stops receiving updates. The
URL scheme moved to `onecare*`, which nothing depends on.

**Things this release leaves genuinely open**, each recorded at more length in
[`CLAUDE.md`](CLAUDE.md):

- **No email address is ever verified.** An account created with a typo has a
  reset path that silently goes to somebody else's mailbox. Self-service reset
  makes that reachable by anybody rather than only by an administrator, and it
  is the gap most worth closing before real customers.
- **The vendor console's emailed recovery is the weakest link by construction.**
  A mailbox is now sufficient to take a console account, and a console account
  can open a break-glass grant against any hospital. The hour-long cooling-off
  delays the part that reaches patient data; it does not prevent it. TOTP on
  `PlatformUser` is the real answer and does not exist.
- **Nothing sweeps expired reset tokens.** Expiry is checked per request so a
  dead link never works, but the table only grows.
- **Neither client has ever rendered against production.** The web app has run
  against a live API in development only; the mobile app has never run on a
  handset at all.
